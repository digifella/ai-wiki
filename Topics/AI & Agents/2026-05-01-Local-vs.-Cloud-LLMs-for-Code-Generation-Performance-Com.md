## Local vs. Cloud LLMs for Code Generation: Performance Comparison for an Interpreter Task
**Clip title:** Cloud vs Local LLMs for Codex/Claude Code - The Truth You Need To Know
**Author / channel:** Gary Explains
**URL:** https://www.youtube.com/watch?v=TMwHAvNQjNw

### Summary
This video explores the viability of using locally run [[concepts/large-language-model-llm|Large Language Models]] (LLMs) as code assistants, aiming to circumvent subscription costs and [[concepts/token-limitations|token limitations]] associated with [[concepts/cloud-based-services|cloud-based services]] like [[entities/openai|OpenAI]]'s [[concepts/codex|Codex]]. The presenter, Gary, used [[entities/ollama|Ollama]] to deploy various models on his personal computer, including [[concepts/23b-parameter-models|Gemma 4]]:26b, [[concepts/qwen3-model|Qwen 3.6]]:35b (on an RTX 5090 GPU), and [[concepts/qwen3-model|Qwen 3.6]]:35b (on a Jetson Thor with a larger [[concepts/context-window|context window]]). The primary goal was to test their ability to generate functional code for a non-trivial programming task.

The main task involved building an interpreter for a custom, simple, typeless scripting language called "nuscpriy" in C, based on a provided `README.md` file that defined its syntax and requirements (including a tokenizer and Abstract Syntax Tree). As a benchmark, the task was first given to OpenAI's [[concepts/codex|Codex]] with [[concepts/3d-game-development|GPT-5]].5. This [[concepts/frontier-model|frontier model]] successfully produced a complete and functional interpreter in just six minutes, even generating additional `nuscpriy` programs for robust stress-[[concepts/testing|testing]], all of which passed or failed as intended.

In stark [[concepts/contrast|contrast]], the local LLMs struggled significantly with the complex [[concepts/interpreter-task|interpreter task]]. [[concepts/23b-parameter-models|Gemma 4]]:26b frequently got stuck, requiring constant "continue" prompts, and eventually entered a repetitive output [[concepts/loop|loop]], leading to its abandonment after multiple restarts. Qwen 3.6:35b also faced similar issues; while it could write some basic code, it encountered bugs with more complex elements. The AI would identify these bugs but then get trapped in a [[concepts/loop|loop]], continuously attempting and failing to fix them, despite the presenter's attempts to restart and guide it. The Jetson Thor-based [[concepts/qwen-model|Qwen model]] showed comparable lack of progress, forcing its abandonment as well.

Recognizing the local LLMs' inability to handle the complex task, Gary then simplified the challenge: building the simplest possible interpreter that included a tokenizer and AST to execute a single line of code like `print(3+4)`. All local models managed to produce code for this simpler task within a few minutes, ranging from 140 to 200 lines. However, they exhibited limitations: Gemma 4:26b only supported the addition operator and processed one line of code; Qwen 3.6:35b added support for subtraction but still only one line; and Qwen 3.6:27b, while supporting all four basic arithmetic operators, had broken [operator precedence](https://en.wikipedia.org/wiki/Order_of_operations). The overall conclusion was one of disappointment, as local LLMs, despite their recent advancements, are not yet capable of matching the robust and sophisticated [[concepts/code-generation|code generation]] capabilities of more advanced, cloud-based models for anything beyond the most basic "plumbing" tasks.
